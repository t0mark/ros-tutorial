우리가 쓴 코드는 쓴 모양 그대로 실행되지 않습니다. CPU가 알아듣는 형태로 바뀌고, 메모리에 올라가 프로세스가 되어야 비로소 동작합니다. 이 과정을 알아야 "프로세스끼리는 왜 서로의 데이터를 직접 볼 수 없는지"를 이해할 수 있습니다.

CPU는 기계어만 안다

CPU가 실제로 실행할 수 있는 것은 "메모리 몇 번지의 값을 가져와라", "두 값을 더해라", "조건이 맞으면 저 번지로 건너뛰어라" 같은 아주 단순한 명령뿐입니다. 이 명령들을 숫자(0과 1)로 나타낸 것을 기계어라고 합니다. 사람이 쓴 코드를 기계어로 바꾸는 방식은 크게 두 가지입니다.

Python 코드가 실행되기까지

터미널에서 python3 hello.py를 입력하면 다음 일이 차례로 일어납니다.

  1. 셸이 새 프로세스를 만들고, 그 안에 /usr/bin/python3 프로그램을 불러옵니다. 이 파일은 C로 작성되어 기계어로 컴파일된 실행 파일입니다.
  2. python3가 hello.py를 읽어 바이트코드로 바꿉니다.
  3. python3 안의 반복문이 바이트코드 명령을 하나씩 꺼내 해당하는 동작을 수행합니다.

즉 CPU가 실제로 실행하는 기계어는 python3 인터프리터의 것이고, 우리가 쓴 코드는 인터프리터가 읽어서 처리하는 데이터에 가깝습니다. 이 차이는 2장의 메모리 구조에서 다시 나옵니다.

확인 문제

CPU가 직접 실행할 수 있는 것은 무엇인가?

기계어뿐입니다. 다른 모든 코드는 컴파일러가 미리 기계어로 바꾸거나, 기계어로 된 인터프리터가 읽어서 대신 실행합니다.

python3 hello.py를 실행했을 때 CPU에서 돌아가는 기계어는 누구의 것인가?

python3 인터프리터의 기계어입니다. hello.py는 바이트코드로 바뀌어 인터프리터가 읽어 처리하는 데이터가 됩니다.

프로그램과 프로세스의 차이는?

프로그램은 디스크에 있는 파일이고, 프로세스는 그 프로그램이 메모리에 올라가 실행 중인 상태입니다. 하나의 프로그램으로 PID가 다른 여러 프로세스를 동시에 실행할 수 있습니다.

셸이 명령을 실행할 때 쓰는 두 단계는?

fork로 자신을 복제해 자식을 만들고, 자식이 exec로 새 프로그램으로 바뀝니다.

가상 메모리: 프로세스마다 자기만의 주소

maps에 나온 주소는 RAM의 실제 위치가 아니라 가상 주소입니다. CPU 안의 MMU라는 장치가 커널이 만든 표(페이지 테이블)를 보고, 가상 주소를 실제 메모리 주소로 바꿔 줍니다. 이 연결은 보통 4KB 크기의 페이지 단위로 이루어집니다.

핵심은 페이지 테이블이 프로세스마다 따로 있다는 점입니다. 두 프로세스가 똑같은 주소 0x5000을 읽어도 각자의 표를 거치므로 서로 다른 실제 메모리에 닿습니다. 다른 프로세스의 메모리는 자기 표에 아예 없으므로, 주소로 가리킬 방법조차 없습니다.

MMUMemory Management Unitpagepage (메모리를 나누는 단위, 보통 4KB)virtualvirtual (가상의)
격리가 주는 이점한 프로세스가 잘못된 주소에 접근하면 커널이 그 프로세스만 Segmentation fault로 끝내고, 다른 프로세스는 아무 영향도 받지 않습니다. 로봇에서 카메라 처리 프로그램이 오류로 죽어도 모터 제어 프로그램은 계속 돌 수 있는 이유가 이것입니다.

확인: fork한 두 프로세스는 메모리를 공유하지 않는다

os.fork()는 지금 프로세스를 통째로 복제해 자식 프로세스를 만듭니다. 복제 직후에는 메모리 내용이 똑같지만, 그 뒤로는 각자의 메모리를 씁니다.

import os

data = [1, 2, 3]
pid = os.fork()                 # 여기서 프로세스가 둘로 갈라짐

if pid == 0:                    # 자식: fork() 가 0 을 돌려줌
    data.append(99)
    print(f"[자식 {os.getpid()}] data = {data}, 주소 = {hex(id(data))}")
else:                           # 부모: fork() 가 자식의 PID 를 돌려줌
    os.waitpid(pid, 0)          # 자식이 끝날 때까지 기다림
    print(f"[부모 {os.getpid()}] data = {data}, 주소 = {hex(id(data))}")
$ python3 fork_memory.py
[자식 7302] data = [1, 2, 3, 99], 주소 = 0x7f3a2c1b8e40
[부모 7301] data = [1, 2, 3], 주소 = 0x7f3a2c1b8e40

id()로 객체의 메모리 주소를 볼 수 있습니다. 두 프로세스에서 data의 주소는 같은데 값은 다릅니다. 같은 가상 주소가 각자의 페이지 테이블을 거쳐 서로 다른 실제 메모리를 가리키기 때문입니다. 자식이 리스트에 99를 넣어도 부모에게는 전혀 보이지 않습니다.

Copy-on-Writefork할 때 메모리를 정말 전부 복사하면 느립니다. 그래서 커널은 처음에는 두 프로세스가 같은 실제 페이지를 읽기 전용으로 함께 쓰게 하고, 어느 한쪽이 쓰는 순간 그 페이지만 복사해 나눠 줍니다. 덕분에 fork가 빠르지만, 결과적으로 서로의 변경이 보이지 않는다는 점은 같습니다.

정리하면, 프로세스 격리는 안정성의 바탕이지만 프로세스끼리 데이터를 나눠야 할 때는 넘을 수 없는 벽이 됩니다. 이 벽을 넘으려면 커널이 따로 마련해 주는 통로가 필요합니다. 그 통로가 프로세스 간 통신(IPC)입니다.

확인 문제

로직 영역과 데이터 영역에는 각각 무엇이 들어가나?

로직 영역(코드, text)에는 CPU가 실행할 기계어 명령이, 데이터 영역(data, BSS, 힙, 스택)에는 전역 변수, 실행 중에 만든 객체, 지역 변수와 함수 호출 기록 같은 값이 들어갑니다.

C의 지역 변수, malloc으로 받은 메모리, Python의 리스트는 각각 어느 영역에 있나?

지역 변수는 스택, malloc으로 받은 메모리는 힙, Python 리스트(를 포함한 모든 Python 객체)는 힙에 있습니다.

/proc/PID/maps에서 권한이 r-xp인 줄은 어떤 영역인가?

실행(x)은 되고 쓰기(w)는 안 되는 영역이므로 코드(text), 즉 로직 영역입니다.

fork 예제에서 부모와 자식의 data 주소가 같은데 값이 다른 이유는?

출력된 주소는 가상 주소이고, 페이지 테이블이 프로세스마다 따로 있어 같은 가상 주소가 서로 다른 실제 메모리를 가리키기 때문입니다. 자식이 쓰는 순간 그 페이지가 복사됩니다(Copy-on-Write).

한 프로세스가 Segmentation fault로 죽으면 다른 프로세스는?

영향이 없습니다. 메모리가 격리되어 있어 잘못된 접근은 그 프로세스 안에서만 일어나고, 커널은 그 프로세스만 끝냅니다.

명령이나 IMU 같은 작은 데이터는 어떤 방법으로 보내도 부담이 없습니다. 하지만 영상과 포인트 클라우드는 초당 수십 MB이므로, 데이터를 몇 번 복사하느냐가 성능을 크게 좌우합니다. 이 차이가 4장(복사하는 방식)과 5장(복사하지 않는 방식)을 나누는 기준입니다.

통신 방법이 갖춰야 할 것

  • 지연 시간(latency): 보낸 뒤 받을 때까지 걸리는 시간. 정지 명령이 0.5초 늦으면 로봇은 이미 벽에 부딪혀 있습니다.
  • 대역폭(bandwidth): 초당 보낼 수 있는 양. 위 표의 카메라 데이터를 감당할 수 있어야 합니다.
  • 신뢰성: 빠짐없이, 순서대로 도착해야 하는가? "임무 시작" 같은 명령은 하나라도 빠지면 안 되지만, 센서 값은 하나 빠지더라도 가장 최신 값을 빨리 받는 것이 더 중요합니다.
  • 1:N 전달: 라이다 데이터 하나를 장애물 인식, 지도 작성, 기록 프로그램이 동시에 받아야 합니다.
  • 동기화: 한쪽이 데이터를 쓰는 도중에 다른 쪽이 읽으면 반쯤 바뀐 데이터를 받게 됩니다.
  • 범위: 같은 컴퓨터 안의 통신인가, 다른 컴퓨터와의 통신인가?

IPC: 커널이 마련해 주는 통로

프로세스는 서로의 메모리를 직접 볼 수 없지만, 모든 프로세스는 시스템 콜로 커널에게 일을 부탁할 수 있습니다. 그래서 모든 IPC는 결국 커널이 만들어 주는 통로입니다. 커널이 데이터를 받아서 상대에게 넘겨주거나(복사), 같은 메모리를 두 프로세스에 함께 연결해 줍니다(공유).

IPCInter-Process Communicationsystem call프로그램이 커널에 기능을 요청하는 방법

모든 통신의 공통 구조: 보내고, 거쳐서, 받는다

앞으로 볼 통신 방법은 여러 가지지만 뼈대는 모두 같습니다. 보내는 쪽이 데이터를 통로에 넣고(①), 받는 쪽이 통로에서 꺼냅니다(②). 방법마다 달라지는 것은 가운데 통로가 무엇인지와 ①, ②에 쓰는 함수뿐입니다.

확인 문제

로봇 소프트웨어를 여러 프로세스로 나누는 이유를 세 가지 들어 보라.

장애 격리(한 부분이 죽어도 나머지 유지), 작업마다 다른 주기, 여러 CPU 코어 활용, 언어·라이브러리 선택의 자유, 재사용과 분업, 여러 컴퓨터로 이루어진 구조 중 세 가지.

640×480 컬러(RGB) 영상을 초당 30장 보내면 초당 데이터는 얼마인가?

640 × 480 × 3 = 921,600바이트(약 0.9MB)이고, 30장이면 약 27.6MB/s입니다.

"임무 시작" 명령과 카메라 영상 중, 빠짐없이 도착하는 것이 더 중요한 것은?

"임무 시작" 명령입니다. 영상은 한 장이 빠지더라도 다음 장이 곧 오므로, 늦게라도 빠짐없이 받는 것보다 최신 장면을 빨리 받는 것이 중요합니다.

프로세스끼리 서로의 메모리를 볼 수 없는데 어떻게 통신할 수 있나?

모든 프로세스는 시스템 콜로 커널과 이야기할 수 있으므로, 커널이 데이터를 대신 전달하거나 같은 메모리를 두 프로세스에 연결해 줍니다.

가장 단순한 방법: 파일

한 프로세스가 파일에 쓰고 다른 프로세스가 그 파일을 읽습니다. 리눅스 첫걸음 7장의 > 재지정으로 결과를 저장해 두고 다른 명령으로 읽는 것도 이 방식입니다. 간단하지만 실시간 통신에는 맞지 않습니다.

  • 받는 쪽은 상대가 언제 새 내용을 썼는지 모릅니다. 계속 파일을 다시 열어 확인(polling)해야 합니다.
  • 상대가 절반쯤 쓴 상태에서 읽으면 깨진 데이터를 받습니다.
  • 저장 장치를 거치므로 메모리끼리 주고받는 것보다 느립니다.

그래서 파일은 기록(로그), 설정, 실행이 끝난 뒤 결과를 넘겨줄 때 주로 씁니다.

파이프

리눅스 첫걸음 7장의 명령1 | 명령2가 바로 파이프입니다. 커널 안에 만든 한 방향 버퍼이고, 한쪽 끝은 쓰기 전용, 다른 끝은 읽기 전용입니다. 이름이 없어서 fork로 끝을 물려받은 부모와 자식 사이에서만 쓸 수 있습니다.

import os

r, w = os.pipe()                # 파이프 생성: 읽기 끝 r, 쓰기 끝 w (둘 다 fd 번호)
pid = os.fork()                 # 자식은 r, w 를 그대로 물려받음

if pid == 0:                    # 자식: 읽는 쪽
    os.close(w)                 # 쓰지 않는 끝은 닫기
    data = os.read(r, 1024)     # 데이터가 올 때까지 기다림
    print(f"자식({os.getpid()})이 받음:", data.decode())
    os.close(r)
    os._exit(0)
else:                           # 부모: 쓰는 쪽
    os.close(r)
    os.write(w, "안녕, 자식 프로세스".encode())
    os.close(w)                 # 다 썼다는 표시 (읽는 쪽에 EOF)
    os.waitpid(pid, 0)
$ python3 pipe_demo.py
자식(7410)이 받음: 안녕, 자식 프로세스

파이프의 성질은 다음과 같습니다.

  • 한 방향입니다. 서로 주고받으려면 파이프를 두 개 만듭니다.
  • 바이트의 흐름입니다. 두 번 나눠 쓴 내용이 한 번에 읽힐 수도 있습니다. 메시지의 경계가 없습니다(7장에서 다시 다룸).
  • 버퍼가 비어 있으면 read가, 가득 차 있으면(리눅스 기본 64KB) write가 기다립니다. 이렇게 함수가 끝나지 않고 기다리는 것을 블로킹이라고 합니다.
  • 쓰는 끝이 모두 닫히면 read는 빈 값 b''를 돌려줍니다. 이것이 EOF(입력 끝)입니다.
pipepipe (관)fdfile descriptorblockingblock (막다): 결과가 나올 때까지 멈춰 기다림_exit뒷정리 없이 즉시 종료 (fork 자식에서 사용)
쓰지 않는 끝은 반드시 닫는다fork하면 부모와 자식이 양쪽 끝을 모두 갖게 됩니다. 자식이 쓰기 끝 w를 닫지 않으면, 부모가 다 쓰고 닫아도 "아직 누군가 쓸 수 있는 끝이 열려 있으므로" EOF가 오지 않아 자식이 영원히 기다립니다.

시그널: 데이터 없는 알림

리눅스 첫걸음 9장의 kill이 보내는 것이 시그널입니다. 시그널은 데이터가 아니라 "이런 일이 일어났다"는 번호 하나만 전달합니다. 시그널을 받은 프로세스는 하던 일을 잠깐 멈추고 미리 등록한 함수(핸들러)를 실행합니다. 핸들러를 등록하지 않았다면 대부분의 시그널은 프로세스를 종료시킵니다.

import os, signal, time

def on_stop(signum, frame):
    print(f"\n{signal.Signals(signum).name} 받음 → 정리하고 종료")
    # 여기서 모터 정지 명령 보내기, 파일 닫기 같은 뒷정리를 함
    raise SystemExit(0)

def on_usr1(signum, frame):
    print("SIGUSR1 받음: 사용자 정의 알림")

signal.signal(signal.SIGINT, on_stop)     # Ctrl+C
signal.signal(signal.SIGTERM, on_stop)    # kill PID
signal.signal(signal.SIGUSR1, on_usr1)    # kill -USR1 PID

print("PID:", os.getpid())
while True:
    time.sleep(1)
# 터미널 1
$ python3 signal_demo.py
PID: 8120
# 터미널 2
$ kill -USR1 8120       # 터미널 1: SIGUSR1 받음: 사용자 정의 알림
$ kill 8120             # 터미널 1: SIGTERM 받음 → 정리하고 종료

Python 코드에서 다른 프로세스에 시그널을 보낼 때는 os.kill(pid, signal.SIGUSR1)처럼 씁니다.

로봇에서 시그널이 중요한 이유로봇 프로그램을 Ctrl+C로 끌 때, 모터에 마지막으로 보낸 속도 명령이 그대로 남아 있으면 로봇이 계속 달릴 수 있습니다. SIGINT 핸들러에서 정지 명령을 보낸 뒤 종료해야 안전합니다. ROS 2 프로그램도 SIGINT를 받아 종료 처리를 합니다. kill -9는 이런 뒷정리를 할 기회조차 주지 않으므로 마지막 수단으로만 씁니다.
시그널은 데이터 전달용이 아니다같은 시그널이 짧은 시간에 여러 번 오면 하나로 합쳐질 수 있고, 번호 말고는 아무것도 실어 보낼 수 없습니다. "무슨 일이 있었다"는 알림에만 쓰고, 데이터는 다른 방법으로 주고받습니다.

kill PID와 kill -9 PID는 프로그램 입장에서 무엇이 다른가?

kill PID는 SIGTERM이라 핸들러로 받아 뒷정리를 하고 끝낼 수 있습니다. kill -9는 SIGKILL이라 잡을 수 없고 즉시 종료되어 뒷정리를 못 합니다.

Python으로 공유 메모리 만들기

Python 표준 라이브러리에 multiprocessing.shared_memory가 있습니다. 리눅스에서는 POSIX 공유 메모리(shm_open)로 만들어지고, /dev/shm 아래에 이름을 가진 파일로 보입니다. 이름으로 찾아 연결하므로 관계없는 프로세스끼리도 쓸 수 있습니다.

import time
from multiprocessing import shared_memory

# robot_data 라는 이름의 100바이트 공유 메모리를 새로 만듦
shm = shared_memory.SharedMemory(name="robot_data", create=True, size=100)
print("만듦:", shm.name, shm.size, "bytes")

try:
    for i in range(30):
        msg = f"count={i}".encode()
        shm.buf[0] = len(msg)                 # 0번 바이트: 메시지 길이
        shm.buf[1:1 + len(msg)] = msg         # 1번 바이트부터: 메시지 내용
        time.sleep(1)
finally:
    shm.close()     # 이 프로세스에서 연결 끊기
    shm.unlink()    # 공유 메모리 자체를 삭제 (만든 쪽이 한 번만)
import time

shm = shared_memory.SharedMemory(name="robot_data")      # 이미 있는 것에 연결
resource_tracker.unregister(shm._name, "shared_memory")  # 읽는 쪽이 끝날 때 공유 메모리가 지워지지 않게

for _ in range(10):
    n = shm.buf[0]
    print("읽음:", bytes(shm.buf[1:1 + n]).decode())
    time.sleep(1)

shm.close()          # 연결만 끊음. 삭제(unlink)는 만든 쪽이 함

shm.buf는 공유 메모리를 바이트 배열처럼 다루게 해 주는 창(memoryview)입니다. 위 예제는 "0번 바이트에 길이, 그 뒤에 내용"이라는 규칙을 두 프로그램이 똑같이 알고 있기 때문에 동작합니다. 공유 메모리는 그냥 바이트 덩어리라서, 이런 배치 규칙을 정하는 것도 프로그래머의 일입니다.

.unlink()이름을 지움. 모두가 close하면 메모리가 해제됨만든 쪽 한 번

numpy 배열을 공유 메모리에 두기

실제로 공유하는 데이터는 대부분 영상이나 포인트 클라우드 같은 숫자 배열입니다. numpy 배열을 만들 때 저장 공간으로 공유 메모리를 지정하면, 배열에 값을 쓰는 순간 다른 프로세스에서도 그 값이 보입니다.

import numpy as np
from multiprocessing import shared_memory

shape, dtype = (480, 640, 3), np.uint8                  # 640x480 컬러 영상 한 장
size = int(np.prod(shape)) * np.dtype(dtype).itemsize   # 921,600 바이트

shm = shared_memory.SharedMemory(name="camera", create=True, size=size)
img = np.ndarray(shape, dtype=dtype, buffer=shm.buf)    # 공유 메모리 위에 만든 배열

img[:] = 0                          # 전체를 검은색으로
img[100:200, 100:200] = (255, 0, 0) # 일부를 빨간색으로 → 바로 상대에게 보임
shm = shared_memory.SharedMemory(name="camera")
img = np.ndarray((480, 640, 3), dtype=np.uint8, buffer=shm.buf)   # 같은 모양과 자료형으로
frame = img.copy()                  # 지금 내용을 내 메모리로 복사해 두고 처리
모양과 자료형은 공유되지 않는다공유되는 것은 921,600개의 바이트뿐입니다. 그것을 "480×640×3 크기의 uint8 배열"로 해석하는 것은 각 프로그램이 정합니다. 한쪽이 (640, 480, 3)으로 잘못 해석하면 오류 없이 엉뚱한 영상이 나옵니다. 이런 "형식의 약속"을 일일이 맞추는 문제는 9장에서 다시 나옵니다.
close 전에 배열부터 지우기공유 메모리 위에 만든 numpy 배열이 남아 있는 상태에서 shm.close()를 부르면 BufferError: cannot close exported pointers exist가 납니다. del img로 배열을 먼저 지운 뒤 close합니다.

close()와 unlink()의 차이는?

close()는 자기 프로세스에서 연결만 끊고, unlink()는 공유 메모리의 이름을 지워 모두가 연결을 끊으면 메모리가 해제되게 합니다. unlink는 만든 쪽이 한 번만 합니다.

공유 메모리로 numpy 배열을 공유할 때 두 프로그램이 반드시 맞춰야 하는 것은?

공유 메모리 이름, 배열의 모양(shape), 자료형(dtype)입니다. 공유되는 것은 바이트뿐이므로 해석 방법을 양쪽이 똑같이 알아야 합니다.

상대의 주소: IP 주소와 포트

IP 주소는 네트워크에서 컴퓨터를 찾는 주소이고, 포트는 그 컴퓨터 안에서 어느 프로세스에게 갈지 정하는 번호(0~65535)입니다. 택배에 비유하면 IP 주소는 건물 주소, 포트는 호수입니다. 그래서 통신 상대는 항상 (IP 주소, 포트) 한 쌍으로 나타냅니다.

IP 주소는 컴퓨터가 아니라 "연결"마다 붙는다

"컴퓨터 한 대에 IP 하나"라고 생각하기 쉽지만, IP 주소는 네트워크 연결(인터페이스)마다 하나씩 붙습니다. 와이파이, 유선 랜선, 가상 연결이 각각 따로 주소를 가집니다. 그래서 컴퓨터 한 대가 IP 주소를 여러 개 갖는 것은 자연스러운 일입니다.

Python의 socket 모듈로 TCP와 UDP 통신을 직접 만들어 봅니다. 여기서는 서버 하나와 클라이언트 하나가 1:1로 주고받는 가장 기본적인 형태만 다룹니다. 예제는 한 컴퓨터에서 터미널 두 개로 실행해도 되고, 127.0.0.1을 상대 IP로 바꾸면 다른 컴퓨터끼리도 그대로 동작합니다.

TCP 통신의 흐름

TCP에는 접속을 기다리는 쪽(서버)과 접속하는 쪽(클라이언트)이 있습니다. 서버가 먼저 준비하고 있어야 클라이언트가 접속할 수 있습니다.

TCP 서버와 클라이언트

import socket

HOST, PORT = "0.0.0.0", 5000      # 0.0.0.0: 이 컴퓨터의 모든 네트워크에서 접속 받기

srv = socket.socket(socket.AF_INET, socket.SOCK_STREAM)          # TCP 소켓
srv.setsockopt(socket.SOL_SOCKET, socket.SO_REUSEADDR, 1)        # 다시 실행할 때 포트 재사용 허용
srv.bind((HOST, PORT))
srv.listen()
print(f"{PORT}번 포트에서 접속을 기다리는 중...")

conn, addr = srv.accept()         # 접속이 올 때까지 여기서 멈춤
print("접속:", addr)
while True:
    data = conn.recv(1024)        # 최대 1024바이트 받기 (올 때까지 기다림)
    if not data:                  # b'' → 상대가 연결을 닫음
        break
    print("받음:", data.decode())
    conn.sendall(b"OK: " + data)  # 받은 내용 앞에 OK 를 붙여 돌려보냄
conn.close()
srv.close()

accept()는 접속한 클라이언트 전용의 새 소켓 conn을 돌려줍니다. 처음 만든 srv는 접속을 받는 데만 쓰고, 실제 데이터는 conn으로 주고받습니다. sendall은 데이터를 전부 보낼 때까지 반복해서 보내 주는 함수이고, send는 일부만 보내고 끝날 수도 있으므로 보통 sendall을 씁니다.

자주 만나는 오류
  • ConnectionRefusedError: 서버가 실행 중이 아니거나, IP·포트가 다릅니다. 서버를 먼저 실행했는지 확인합니다.
  • OSError: [Errno 98] Address already in use: 같은 포트를 다른 프로세스가 쓰고 있거나, 방금 끈 서버의 연결이 아직 정리 중입니다. SO_REUSEADDR 설정으로 대부분 해결되고, 다른 프로세스가 쓰고 있다면 ss -tlnp로 찾습니다.
  • 같은 컴퓨터에서는 되는데 다른 컴퓨터에서 안 될 때: 서버가 127.0.0.1로 bind했는지, 두 컴퓨터가 같은 네트워크인지(ping), 방화벽(sudo ufw status)이 막고 있지 않은지 확인합니다.

메시지 경계 문제

TCP는 바이트의 흐름입니다(4장의 파이프와 같음). sendall 한 번이 recv 한 번과 짝지어진다는 보장이 없습니다. 클라이언트가 "hello"와 "world"를 빠르게 연달아 보내면, 서버는 "helloworld"를 한 번에 받을 수도 있고 "hel"과 "loworld"로 나눠 받을 수도 있습니다. 위의 예제가 잘 동작한 것은 클라이언트가 매번 응답을 기다렸다가 다음 것을 보냈기 때문입니다.

그래서 실제로는 메시지 하나가 어디서 끝나는지를 보내는 쪽과 받는 쪽이 약속해야 합니다. 대표적인 방법은 두 가지입니다.

  • 끝 표시: 메시지마다 끝에 줄바꿈(\n)을 붙이고, 받는 쪽은 줄 단위로 읽습니다.
  • 길이 머리말: 메시지 앞에 "이 메시지는 몇 바이트"라는 고정 크기 숫자를 붙이고, 받는 쪽은 그 길이만큼 모아서 읽습니다.

또 하나의 약속은 내용의 형식입니다. 메모리 속의 값(딕셔너리, 숫자)을 바이트 줄로 바꾸는 것을 직렬화, 그 반대를 역직렬화라고 합니다. 아래는 JSON으로 직렬화하고 줄바꿈으로 경계를 나누는 예입니다.

import json

msg = {"linear": 0.5, "angular": 0.1}               # 직진 0.5 m/s, 회전 0.1 rad/s
cli.sendall((json.dumps(msg) + "\n").encode())       # 메시지 하나 = JSON 한 줄
import json

f = conn.makefile("r", encoding="utf-8")    # 소켓을 파일처럼 줄 단위로 읽기
for line in f:                              # 한 줄 = 메시지 하나. 연결이 닫히면 반복 끝
    msg = json.loads(line)
    print(msg["linear"], msg["angular"])

import socket

sock = socket.socket(socket.AF_INET,
                     socket.SOCK_DGRAM)   # UDP
sock.bind(("0.0.0.0", 6000))

while True:

import socket, time

sock = socket.socket(socket.AF_INET,
                     socket.SOCK_DGRAM)
for i in range(5):
    # 연결 없이 주소를 적어 바로 보냄
    sock.sendto(f"scan {i}".encode(),
                ("127.0.0.1", 6000))
    time.sleep(0.1)

TCP와 비교하면 다음이 다릅니다.

  • listen, accept, connect가 없습니다. 보낼 때마다 sendto에 상대 주소를 적고, 받을 때는 recvfrom이 보낸 쪽 주소를 함께 알려 줍니다.
  • 받는 쪽이 실행 중이 아니어도 sendto는 오류 없이 끝납니다. 데이터는 그냥 사라집니다.
  • 데이터그램 단위로 도착하므로 메시지 경계 문제가 없습니다. 대신 빠지거나 순서가 바뀔 수 있습니다.
  • 데이터그램 하나의 크기에는 한계가 있습니다. 패킷 크기(약 1500바이트)를 넘으면 여러 조각으로 나뉘고, 그중 하나만 사라져도 전체를 잃습니다. 큰 데이터는 직접 나눠 보내야 합니다.

같은 컴퓨터 안의 소켓: Unix 도메인 소켓

AF_UNIX를 쓰면 주소가 (IP, 포트) 대신 파일 경로가 됩니다. 네트워크 계층을 거치지 않으므로 같은 컴퓨터 안에서는 127.0.0.1로 TCP 통신을 하는 것보다 가볍습니다. 코드는 주소 부분만 다르고 나머지는 거의 같습니다.

# 서버
srv = socket.socket(socket.AF_UNIX, socket.SOCK_STREAM)
srv.bind("/tmp/robot.sock")     # 이 경로에 소켓 파일이 생김 (ls -l 하면 맨 앞이 s)
srv.listen()
# 클라이언트
cli = socket.socket(socket.AF_UNIX, socket.SOCK_STREAM)
cli.connect("/tmp/robot.sock")
소켓 파일 지우기서버를 끈 뒤에도 소켓 파일이 남아 있으면 다시 bind할 때 Address already in use가 납니다. 서버 시작 전에 os.unlink(경로)로 지워 둡니다. 도커, 데스크톱 화면 서버 같은 많은 프로그램이 이 방식으로 같은 컴퓨터의 프로세스와 통신합니다.

TCP 서버가 접속을 받기까지 부르는 함수를 순서대로 쓰면?

socket() → bind() → listen() → accept()

서버의 recv()가 b''를 돌려주었다. 무슨 뜻인가?

상대(클라이언트)가 연결을 닫았다는 뜻입니다. 반복을 끝내고 소켓을 닫습니다.

sendall을 두 번 했는데 받는 쪽 recv 한 번에 두 메시지가 붙어서 왔다. 이유와 해결 방법은?

TCP는 메시지 경계가 없는 바이트 흐름이기 때문입니다. 메시지마다 줄바꿈 같은 끝 표시를 붙이거나, 앞에 길이를 붙여서 받는 쪽이 경계를 나누게 합니다.

UDP로 sendto를 했는데 받는 프로그램이 실행 중이 아니었다. 어떻게 되나?

보내는 쪽에는 오류가 나지 않고, 데이터는 그대로 사라집니다.

JSON 대신 struct로 직렬화할 때 장점과 단점은?

크기가 작고 빠릅니다. 대신 사람이 읽기 어렵고, 값의 순서·자료형을 양쪽이 정확히 맞춰야 하며 한쪽만 바꾸면 잘못 해석됩니다.

고르는 순서

  1. 같은 컴퓨터인가? 아니라면 소켓(TCP 또는 UDP)밖에 없습니다.
  2. 데이터가 크고 자주 오가는가? (초당 MB 단위) 같은 컴퓨터라면 공유 메모리를 씁니다. 다만 한쪽이 쓰는 도중에 다른 쪽이 읽지 않도록 조심해야 합니다.
  3. 작은 데이터를 1:1로? 부모-자식 사이면 파이프, 아니면 Unix 소켓을 씁니다.
  4. 알림만 필요한가? 시그널을 씁니다.
  5. 네트워크라면 빠짐없이 도착해야 하면 TCP, 최신 값이 중요하면 UDP를 씁니다.

DDS: ROS 아래에서 실제로 통신하는 것

ROS 2는 통신 기능을 직접 만들지 않고 DDS라는 통신 표준을 가져다 씁니다. DDS는 원래 군사·항공·공장 설비처럼 많은 장비가 데이터를 실시간으로 주고받아야 하는 곳에서 쓰던 발행/구독 표준입니다. 우리가 publish를 부르면 그 아래에서 일어나는 일은 다음과 같습니다.

DDS가 해 주는 일은 크게 세 가지입니다.

  • 자동 탐색: 프로그램이 켜지면 DDS가 같은 네트워크에 UDP 멀티캐스트(여럿에게 한꺼번에 보내기)로 "나는 /scan을 보낸다", "나는 /scan을 받고 싶다"고 알립니다. 이름이 맞는 상대끼리 서로의 주소를 알아내 연결하므로, 코드에 IP 주소를 적을 필요가 없고 어느 쪽을 먼저 켜도 됩니다.
  • 직렬화: 보낼 데이터를 바이트 줄로 바꾸고, 받는 쪽에서 다시 원래 값으로 되돌립니다. 7장에서 JSON과 struct로 직접 하던 일입니다.
  • 전송 방법 선택: 상대가 같은 컴퓨터에 있으면 공유 메모리로, 다른 컴퓨터에 있으면 UDP로 보냅니다(Fast DDS 기본 설정 기준). 8장에서 상황마다 직접 고르던 일입니다.

rmw는 DDS 구현을 바꿔 끼울 수 있게 해 주는 층입니다. DDS 구현은 Fast DDS 말고도 여러 가지가 있는데, 환경 변수 하나(RMW_IMPLEMENTATION)로 다른 것을 골라도 내 코드는 그대로입니다.

코드로 비교하기

7장의 소켓 예제와 같은 일, 즉 한쪽이 문자열을 보내고 다른 쪽이 받는 프로그램을 ROS 2로 쓰면 다음과 같습니다. 통신에 관련된 줄만 보면 됩니다.

import rclpy
from rclpy.node import Node
from std_msgs.msg import String          # 보낼 데이터의 형식: 문자열 하나

class Talker(Node):
    def __init__(self):
        super().__init__("talker")
        self.pub = self.create_publisher(String, "chatter", 10)     # "chatter" 라는 이름으로 보낼 준비
        self.timer = self.create_timer(0.5, self.tick)              # 0.5초마다 tick 호출
        self.n = 0

    def tick(self):
        msg = String()
        msg.data = f"hello {self.n}"
        self.pub.publish(msg)                                       # ① 보내기: 누가 받는지 모름
        print("보냄:", msg.data)
        self.n += 1

rclpy.init()
rclpy.spin(Talker())        # 타이머 시간이 되면 tick 을 불러 주며 계속 실행
import rclpy
from rclpy.node import Node
from std_msgs.msg import String

class Listener(Node):
    def __init__(self):
        super().__init__("listener")
        self.create_subscription(String, "chatter", self.on_msg, 10)  # "chatter" 를 받겠다고 등록

    def on_msg(self, msg):                     # ② 받기: 데이터가 올 때마다 불림
        print("받음:", msg.data)

rclpy.init()
rclpy.spin(Listener())      # 데이터가 오기를 기다리다가 on_msg 를 불러 줌
# 두 터미널 모두 먼저 ROS 2 환경을 불러옴 (.bashrc 에 넣어 두었다면 생략)
$ source /opt/ros/humble/setup.bash

$ python3 talker.py
보냄: hello 0

# 터미널 2

7장의 코드와 비교하면 없는 것이 눈에 띕니다. IP 주소, 포트, bind, connect, accept, encode, JSON, 줄바꿈 처리, 재접속 코드가 하나도 없습니다. 대신 이름("chatter")과 데이터 형식(String)만 있습니다.

  • talker와 listener 중 어느 것을 먼저 실행해도 됩니다. DDS의 자동 탐색이 서로를 찾아 줍니다.
  • listener를 두 개 띄우면 둘 다 같은 데이터를 받습니다.
  • 두 프로그램을 같은 네트워크의 다른 컴퓨터에서 실행해도 코드를 고칠 필요가 없습니다. 같은 컴퓨터면 공유 메모리, 다른 컴퓨터면 UDP로 DDS가 알아서 바꿉니다.
spin과 받는 함수7장의 서버는 recv()를 직접 부르고 거기서 기다렸습니다. ROS 2에서는 rclpy.spin()이 대신 기다리다가 데이터가 오면 등록해 둔 함수(on_msg)를 불러 줍니다. 이렇게 "일이 생기면 불러 달라고 맡겨 두는 함수"를 콜백이라고 합니다. create_publisher와 create_subscription의 마지막 숫자 10은 지금은 신경 쓰지 않아도 됩니다.

확인 문제

ROS는 운영체제인가?

아닙니다. 리눅스 같은 운영체제 위에서 동작하는 통신 미들웨어입니다.

소켓 통신과 ROS 통신에서 "상대를 정하는 방법"은 어떻게 다른가?

소켓은 상대의 IP 주소와 포트를 직접 지정하고, ROS는 통로의 이름만 정합니다. 같은 이름을 쓰는 상대는 DDS가 찾아서 연결해 줍니다.

talker와 listener 중 무엇을 먼저 실행해야 하나?

상관없습니다. DDS의 자동 탐색이 서로를 찾아 연결합니다. (7장의 TCP에서는 서버를 먼저 실행해야 했습니다.)

같은 컴퓨터에 있는 두 프로그램 사이의 데이터는 보통 어떻게 전달되나? 다른 컴퓨터라면?

Fast DDS 기본 설정에서는 같은 컴퓨터면 공유 메모리, 다른 컴퓨터면 UDP를 씁니다.

DDS가 해 주는 세 가지 일은?

자동 탐색(상대 찾기), 직렬화(데이터를 바이트로 바꾸고 되돌리기), 전송 방법 선택(공유 메모리 또는 UDP).
