확인 문제

ROS는 Windows나 Ubuntu 같은 운영체제인가?

아닙니다. Ubuntu 같은 운영체제 위에 설치해서 쓰는 로봇 소프트웨어 플랫폼입니다. 통신 미들웨어, 표준 메시지, 빌드·실행 도구, 개발 도구, 공개 패키지를 함께 제공합니다.

라이다를 다른 회사 제품으로 바꿔도 장애물 인식 프로그램을 고치지 않아도 되는 이유는?

드라이버가 장치마다 다른 부분을 감추고 표준 메시지(sensor_msgs/LaserScan)로 데이터를 내보내기 때문입니다. 장애물 인식 프로그램은 표준 메시지만 받으므로 드라이버만 바꾸면 됩니다.

Ubuntu 22.04에 설치하는 ROS 2 LTS 배포판의 이름은?

설치하면 어디에 무엇이 생기나

공식 설치 문서(docs.ros.org의 Ubuntu (deb packages))를 따라 apt로 설치하면, ROS 2의 모든 파일은 /opt/ros/humble/ 한 곳에 들어갑니다. 리눅스 첫걸음 2장에서 본 것처럼 /opt는 추가로 설치하는 프로그램을 두는 곳입니다.

$ ls /opt/ros/humble
bin  include  lib  local  opt  setup.bash  setup.sh  setup.zsh  share  ...
디렉터리들어 있는 것
bin/ros2, rviz2 같은 명령 (실행 파일)
lib/패키지별 실행 파일(lib/패키지/노드), Python 모듈(lib/python3.10/site-packages), ROS 2 내부 라이브러리(.so)
share/패키지별 설정, launch 파일, 메시지 정의, package.xml
setup.bash이 설치본을 쓸 수 있게 환경 변수를 설정하는 스크립트

source가 하는 일

새 터미널에서 바로 ros2를 입력하면 셸이 명령을 찾지 못합니다. 셸은 PATH 환경 변수에 적힌 디렉터리에서만 명령을 찾는데(리눅스 첫걸음 8장), /opt/ros/humble/bin은 거기에 없기 때문입니다.

$ ros2
ros2: command not found
$ source /opt/ros/humble/setup.bash
$ which ros2
/opt/ros/humble/bin/ros2
$ printenv | grep -E '^(ROS|AMENT)'       # ROS 관련 환경 변수만 보기
ROS_VERSION=2
ROS_PYTHON_VERSION=3
ROS_DISTRO=humble
AMENT_PREFIX_PATH=/opt/ros/humble
...

setup.bash는 여러 환경 변수에 ROS 2의 경로를 추가합니다. source로 실행하는 이유는, 일반 실행(bash setup.bash)은 자식 프로세스에서 돌기 때문에 거기서 바꾼 환경 변수가 지금 셸에 남지 않기 때문입니다(리눅스 첫걸음 8장).

환경 변수는 터미널마다 따로환경 변수는 그 셸(프로세스)에만 적용됩니다. 한 터미널에서 source했다고 다른 터미널까지 바뀌지 않으므로, ROS 2를 쓰는 터미널마다 환경이 불러와져 있어야 합니다. 또 한 터미널에서 서로 다른 배포판의 setup.bash를 둘 다 source하면 경로가 섞여 알 수 없는 오류가 납니다.

ROS_DOMAIN_ID: 같은 네트워크에서 서로 섞이지 않게

ROS 2는 같은 네트워크에 있는 노드를 자동으로 찾아 연결합니다(IPC 10장). 편리하지만, 동아리방이나 학교처럼 여러 사람이 같은 와이파이에서 ROS 2를 쓰면 남의 노드와 토픽까지 보이고 섞이는 문제가 생깁니다. 다른 사람이 보낸 속도 명령에 내 로봇이 움직일 수도 있습니다.

ROS_DOMAIN_ID는 ROS 2 통신을 번호로 나누는 환경 변수입니다. DDS는 이 번호로 탐색과 통신에 쓸 UDP 포트 번호를 계산하므로, 번호가 다르면 서로를 아예 발견하지 못합니다. 설정하지 않으면 0입니다.

$ export ROS_DOMAIN_ID=7          # 0~101 사이에서 팀이나 사람마다 다른 번호를 정함
$ echo $ROS_DOMAIN_ID
7
통신이 안 될 때 먼저 볼 것두 터미널(또는 두 컴퓨터)에서 노드끼리 연결되지 않으면 양쪽의 echo $ROS_DOMAIN_ID부터 확인합니다. 한쪽 터미널에서만 설정한 경우가 흔합니다. 반대로 내 컴퓨터 안에서만 통신하고 싶다면 export ROS_LOCALHOST_ONLY=1로 다른 컴퓨터와의 통신을 막을 수 있습니다.
domaindomain (영역)ROS_LOCALHOST_ONLYlocalhost(127.0.0.1)로만 통신

확인 문제

apt로 설치한 ROS 2 Humble의 파일은 어디에 있나?

/opt/ros/humble/ 아래에 있습니다. 명령은 bin/, 라이브러리와 실행 파일은 lib/, 설정과 메시지 정의는 share/에 있습니다.

source /opt/ros/humble/setup.bash를 하지 않은 터미널에서 ros2가 "command not found"인 이유는?

PATH에 /opt/ros/humble/bin이 없어서 셸이 ros2 실행 파일을 찾지 못하기 때문입니다. setup.bash가 PATH를 포함한 여러 환경 변수에 ROS 2 경로를 추가합니다.

setup.bash를 bash setup.bash로 실행하면 왜 효과가 없나?

bash로 실행하면 새 자식 셸에서 실행되고, 그 셸이 끝나면서 바꾼 환경 변수도 사라집니다. 지금 셸의 환경을 바꾸려면 source로 현재 셸에서 실행해야 합니다.

/opt/ros/humble/setup.bash와 ~/ros2_ws/install/setup.bash 중 무엇을 먼저 source해야 하나?

/opt/ros/humble/setup.bash(underlay)를 먼저, 내 워크스페이스(overlay)를 나중에 source합니다. 나중에 source한 쪽이 우선하므로 내 패키지가 기본 패키지보다 먼저 쓰입니다.

옆 사람과 같은 와이파이에서 turtlesim을 켰더니 옆 사람의 키보드 입력에 내 거북이가 움직인다. 해결 방법은?

서로 다른 ROS_DOMAIN_ID를 설정합니다. 도메인 번호가 다르면 DDS가 서로를 발견하지 못하므로 통신이 분리됩니다.

노드: 실행의 최소 단위

노드(node)는 한 가지 일을 맡는 실행 단위입니다. 카메라 영상을 내보내는 노드, 위치를 추정하는 노드, 모터에 명령을 보내는 노드처럼 기능별로 나눕니다. 보통 노드 하나가 프로세스 하나이고(한 프로세스에 노드 여럿을 넣을 수도 있습니다), IPC 자료 3장에서 본 "로봇 소프트웨어를 여러 프로세스로 나누는 이유"가 그대로 노드를 나누는 이유입니다.

turtlesim은 ROS 학습용으로 만든 아주 작은 시뮬레이터입니다. 창 안의 거북이가 로봇 역할을 합니다. 노드 두 개를 실행해 봅니다.

$ ros2 run turtlesim turtlesim_node

teleopteleoperation (원격 조종)cmd_velcommand velocity (속도 명령)posepose (위치 + 방향, 자세)

키보드 노드 대신 내가 만든 자율주행 노드가 같은 /turtle1/cmd_vel에 발행하면, turtlesim 쪽 코드는 하나도 고치지 않아도 거북이가 내 노드의 명령대로 움직입니다. 실제 로봇에서도 마찬가지로, 모터 드라이버 노드는 /cmd_vel만 구독하고 그 명령을 사람이 보냈는지 자율주행 알고리즘이 보냈는지는 신경 쓰지 않습니다.

이름 규칙과 네임스페이스

노드, 토픽, 서비스, 액션은 모두 파일 경로처럼 /로 구분된 이름을 가집니다. 앞부분은 무리를 나누는 네임스페이스(namespace)입니다. /turtle1/cmd_vel은 turtle1 네임스페이스 안의 cmd_vel입니다.

리눅스 경로와 비교리눅스 첫걸음 2장의 절대 경로(/home/user)와 상대 경로(docs)와 같은 원리입니다. 다만 ROS 이름에는 .. 같은 위로 올라가는 표기가 없습니다.

확인 문제

ROS 2에서 "노드"란 무엇인가?

한 가지 기능을 맡는 실행 단위입니다. 보통 프로세스 하나가 노드 하나이며, 노드끼리 Topic, Service, Action으로 메시지를 주고받습니다.

로봇의 현재 속도를 초당 50번 다른 노드들에게 알려야 한다. 어떤 통신 방식이 알맞나?

Topic입니다. 끝없이 계속 흘러가는 데이터이고, 여러 노드가 동시에 받을 수 있어야 하기 때문입니다.

"지도 저장해 줘"와 "부엌까지 가 줘" 중 Action이 더 알맞은 것은? 이유는?

"부엌까지 가 줘"입니다. 오래 걸리는 일이라 이동 중에 남은 거리 같은 중간 보고가 필요하고, 도중에 취소할 수도 있어야 하기 때문입니다. 지도 저장처럼 금방 끝나는 일은 Service로 충분합니다.

turtle_teleop_key 노드와 turtlesim_node 노드는 무엇으로 연결되나?

/turtle1/cmd_vel이라는 토픽 이름으로 연결됩니다. 키보드 노드가 그 토픽에 속도 메시지를 발행하고, turtlesim 노드가 구독합니다.

네임스페이스가 /robot2인 노드가 코드에서 odom이라는 토픽을 발행하면 실제 토픽 이름은? /odom이라고 썼다면?

odom은 상대 이름이므로 /robot2/odom이 됩니다. /odom은 절대 이름이므로 네임스페이스와 상관없이 /odom입니다.

파라미터는 노드마다 따로 있으므로 노드 이름을 함께 씁니다. use_sim_time은 모든 노드에 자동으로 있는 파라미터로, 컴퓨터의 시계 대신 시뮬레이터나 bag 재생(5장)이 알려 주는 시간을 쓸지 정합니다.

확인 문제

처음 보는 노드가 어떤 토픽을 받고 내보내는지 알고 싶다. 어떤 명령을 쓰나?

ros2 node info /노드이름입니다. 구독하는 토픽, 발행하는 토픽, 제공하는 서비스와 액션을 한 번에 보여 줍니다.

센서 노드를 켰는데 다른 노드가 데이터를 못 받는다. 센서 쪽이 제대로 발행하고 있는지 확인하는 명령 두 가지는?

ros2 topic echo /토픽으로 내용이 나오는지, ros2 topic hz /토픽으로 기대한 주기로 나오는지 확인합니다. ros2 topic info로 발행자 수가 1 이상인지도 볼 수 있습니다.

geometry_msgs/msg/Twist에서 바퀴 달린 로봇의 전진 속도와 회전 속도는 각각 어느 필드인가?

전진 속도는 linear.x(m/s), 제자리 회전 속도는 angular.z(rad/s)입니다.

서비스 형식과 액션 형식에서 ---은 각각 무엇을 나누나?

서비스는 요청 / 응답, 액션은 목표 / 결과 / 피드백을 나눕니다.

ros2 topic pub /turtle1/cmd_vel ...에서 --once를 빼면 어떻게 되나?

기본 주기(1Hz)로 Ctrl+C를 누를 때까지 같은 메시지를 계속 발행합니다.

지금까지는 ROS 2에 들어 있는 노드를 실행만 했습니다. 직접 만든 노드를 ros2 run으로 실행하려면 코드를 패키지로 묶고, 워크스페이스에서 빌드해야 합니다. Python은 컴파일이 필요 없는데도 왜 빌드를 하는지, 그 과정에서 어떤 파일이 어디로 가는지를 이해하는 것이 이 장의 목표입니다.

패키지와 워크스페이스

  • 패키지(package): ROS 2에서 코드를 나누고 배포하는 단위입니다. 노드 코드, launch 파일, 설정 파일, 그리고 "이 패키지가 어떤 다른 패키지를 쓰는지"(의존성)가 한 패키지에 들어갑니다. turtlesim도 패키지 하나입니다.
  • 워크스페이스(workspace): 내 패키지들을 모아 두고 한꺼번에 빌드하는 디렉터리입니다. 이름은 자유지만 보통 ~/ros2_ws를 쓰고, 패키지 소스는 반드시 그 안의 src/에 둡니다.

$ ls

Python인데 왜 빌드하나

Python 파일은 python3 파일.py로 바로 실행할 수 있습니다. 그런데도 빌드(정확히는 설치)를 하는 이유는, ROS 2 도구들이 소스 디렉터리가 아니라 정해진 설치 위치에서 파일을 찾기 때문입니다.

도구찾는 곳
ros2 run 패키지 실행파일install/패키지/lib/패키지/실행파일
ros2 launch 패키지 파일install/패키지/share/패키지/launch/
Python의 import 패키지install/패키지/lib/python3.10/site-packages/
설정 파일 경로 찾기 (10장)install/패키지/share/패키지/

빌드는 이 위치들로 파일을 옮기고, 실행 스크립트를 만들고, 패키지 목록에 등록하는 일입니다. 정해진 자리에 놓여 있기 때문에 다른 사람의 컴퓨터에서도, 다른 디렉터리에서도 같은 명령으로 실행할 수 있습니다.

package.xml: 패키지의 신분증

package.xml에는 패키지 이름, 버전, 설명, 관리자, 라이선스, 그리고 의존성(이 패키지가 쓰는 다른 패키지)을 적습니다. colcon은 의존성을 보고 패키지들의 빌드 순서를 정하고, rosdep(아래)은 이것을 보고 필요한 패키지를 설치합니다.

<package format="3">
  <name>my_py_pkg</name>
  <version>0.0.0</version>
  <description>TODO: Package description</description>
  <maintainer email="me@example.com">me</maintainer>
  <license>Apache-2.0</license>

  <depend>rclpy</depend>                  <!-- 코드에서 import 하는 ROS 패키지 -->
  <depend>std_msgs</depend>
  <exec_depend>turtlesim</exec_depend>    <!-- 실행할 때만 필요 (launch 에서 띄우는 노드 등) -->

  <export>
    <build_type>ament_python</build_type>
  </export>
</package>
의존성을 빠뜨려도 빌드는 된다Python은 컴파일하지 않으므로 의존성을 빠뜨려도 내 컴퓨터에서는 빌드와 실행이 됩니다(이미 설치되어 있으니까요). 문제는 다른 컴퓨터에서 rosdep으로 설치할 때 그 패키지가 빠진다는 것입니다. 코드에서 import하는 ROS 패키지는 빠짐없이 <depend>로 적어 둡니다.

노드 코드의 뼈대

모든 rclpy 노드는 같은 뼈대를 가집니다. 1초마다 로그를 찍는 가장 작은 노드입니다.

import rclpy
from rclpy.node import Node


class HelloNode(Node):                      # 노드 = Node 를 상속한 클래스
    def __init__(self):
        super().__init__('hello_node')                     # 노드 이름
        self.timer = self.create_timer(1.0, self.on_timer) # 1초마다 on_timer 호출 예약
        self.count = 0

    def on_timer(self):                     # 콜백: 때가 되면 불림
        self.get_logger().info(f'hello {self.count}')
        self.count += 1


def main(args=None):
    rclpy.init(args=args)       # ① ROS 2 통신 준비
    node = HelloNode()          # ② 노드 생성: 타이머·발행자·구독자 등록
    rclpy.spin(node)            # ③ 이벤트를 기다리며 콜백 호출 (Ctrl+C 까지)
    node.destroy_node()         # ④ 정리
    rclpy.shutdown()


if __name__ == '__main__':
    main()

        'hello = my_py_pkg.hello_node:main',    # 실행 파일 hello → my_py_pkg/hello_node.py 의 main() 실행

rosdep: 의존 패키지 한꺼번에 설치

다른 사람이 만든 패키지를 받아 빌드하면, 필요한 패키지가 설치되어 있지 않아 실패하는 경우가 많습니다. rosdep은 워크스페이스 안 모든 package.xml의 의존성을 읽어서, 빠진 것을 apt로 한꺼번에 설치해 줍니다.

$ sudo rosdep init          # 처음 한 번만
$ rosdep update
$ cd ~/ros2_ws
$ rosdep install --from-paths src --ignore-src -y
# --from-paths src: src 안의 package.xml 을 모두 읽음
# --ignore-src: 워크스페이스에 소스로 있는 패키지는 apt 로 설치하지 않음
# -y: 설치 여부를 묻지 않음

확인 문제

Python 코드는 컴파일이 필요 없는데 왜 colcon build를 하나?

ros2 run, ros2 launch 같은 도구는 소스가 아니라 install/ 아래 정해진 위치에서 실행 파일과 launch·설정 파일을 찾기 때문입니다. 빌드는 파일을 그 위치로 설치하고 실행 스크립트를 만들어 패키지를 등록하는 과정입니다.

워크스페이스에서 git으로 관리해야 하는 디렉터리는? build, install, log는 왜 아닌가?

src/만 관리합니다. 나머지 셋은 colcon이 소스로부터 언제든 다시 만들 수 있는 결과물이기 때문입니다.

노드의 생성자(__init__)에서 하는 일과 콜백에서 하는 일은 어떻게 다른가?

생성자에서는 타이머, 발행자, 구독자를 등록만 합니다. 실제 처리는 spin()이 타이머 만료나 메시지 도착 때 불러 주는 콜백 안에서 일어납니다.

Python 노드 파일을 새로 만들었는데 ros2 run 패키지 노드가 "No executable found"라고 한다. 무엇을 빠뜨렸을까?

setup.py의 entry_points에 실행 파일을 등록하지 않았거나, 등록한 뒤 다시 빌드하고 source install/setup.bash를 하지 않은 것입니다.

--symlink-install로 빌드했을 때, 이미 등록된 노드의 코드를 고친 뒤 다시 빌드해야 하나?

아닙니다. install/에 원본 파일을 가리키는 링크가 있으므로, 원본을 고치면 바로 반영됩니다. 단, 실행 파일을 새로 등록하거나 새 파일을 추가했다면 다시 빌드해야 합니다.

발행자와 구독자

6장의 뼈대에서 생성자에 발행자나 구독자를 등록하는 줄만 더하면 됩니다.

import rclpy
from rclpy.node import Node
from std_msgs.msg import String             # 메시지 형식 가져오기


class Talker(Node):
    def __init__(self):
        super().__init__('talker')
        self.pub = self.create_publisher(String, 'chatter', 10)   # 형식, 토픽 이름, QoS(큐 크기)
        self.timer = self.create_timer(0.5, self.on_timer)        # 0.5초마다 발행
        self.count = 0

    def on_timer(self):
        msg = String()
        msg.data = f'Hello World: {self.count}'
        self.pub.publish(msg)                                     # 누가 받는지는 모름
        self.get_logger().info(f'Publishing: "{msg.data}"')
        self.count += 1


def main(args=None):
    rclpy.init(args=args)
    node = Talker()
    rclpy.spin(node)
    node.destroy_node()
    rclpy.shutdown()
import rclpy
from rclpy.node import Node
from std_msgs.msg import String


class Listener(Node):
    def __init__(self):
        super().__init__('listener')
        self.sub = self.create_subscription(String, 'chatter', self.on_msg, 10)

    def on_msg(self, msg):                  # 구독 콜백: 메시지가 올 때마다 불림
        self.get_logger().info(f'I heard: "{msg.data}"')


def main(args=None):
    rclpy.init(args=args)
    node = Listener()
    rclpy.spin(node)
    node.destroy_node()
    rclpy.shutdown()

QoS: 통신 품질 설정

create_publisher(String, 'chatter', 10)의 마지막 숫자 10은 QoS 설정을 줄여 쓴 것입니다. QoS는 "메시지를 어떻게 전달할지"에 대한 약속으로, 발행자와 구독자가 각자 정합니다. 중요한 항목은 세 가지입니다.

항목선택지뜻
History / Depth
몇 개 보관하나		KEEP_LAST + 개수최근 N개만 보관. 받는 쪽이 느리면 오래된 것부터 버림. 숫자 10이 이것
KEEP_ALL전부 보관 (메모리 한도까지)
Reliability
잃어버리면?		RELIABLE도착을 확인하고, 빠지면 다시 보냄. TCP와 비슷 (IPC 6장)
BEST_EFFORT한 번 보내고 끝. 빠져도 다시 안 보냄. UDP와 비슷. 지연이 적음
Durability

서버

import rclpy
from rclpy.node import Node
from example_interfaces.srv import AddTwoInts


class AddServer(Node):
    def __init__(self):
        super().__init__('add_two_ints_server')
        self.srv = self.create_service(AddTwoInts, 'add_two_ints', self.on_request)

    def on_request(self, request, response):        # 요청이 올 때마다 불림
        response.sum = request.a + request.b
        self.get_logger().info(f'요청: {request.a} + {request.b}')
        return response                             # 반환한 response 가 클라이언트로 감


def main():
    rclpy.init()
    rclpy.spin(AddServer())
    rclpy.shutdown()

클라이언트와 Future

import sys
import rclpy
from rclpy.node import Node
from example_interfaces.srv import AddTwoInts


class AddClient(Node):
    def __init__(self):
        super().__init__('add_two_ints_client')
        self.cli = self.create_client(AddTwoInts, 'add_two_ints')
        while not self.cli.wait_for_service(timeout_sec=1.0):      # 서버가 뜰 때까지 대기
            self.get_logger().info('서버를 기다리는 중...')

    def send(self, a, b):
        req = AddTwoInts.Request()
        req.a, req.b = a, b
        return self.cli.call_async(req)             # 요청을 보내고 Future 를 바로 돌려받음


def main():
    rclpy.init()
    node = AddClient()
    future = node.send(int(sys.argv[1]), int(sys.argv[2]))
    rclpy.spin_until_future_complete(node, future)  # 응답이 올 때까지 spin
    node.get_logger().info(f'결과: {future.result().sum}')
    node.destroy_node()
    rclpy.shutdown()

call_async()는 요청을 보내자마자 Future라는 "나중에 결과가 담길 상자"를 돌려줍니다. 응답은 아직 오지 않았으므로 상자는 비어 있습니다. 응답 메시지가 도착해도 누군가 그것을 처리해 줘야 상자가 채워지는데, 그 일을 하는 것이 spin입니다. 그래서 spin_until_future_complete()로 "상자가 찰 때까지 spin"합니다.

asyncasynchronous (비동기: 기다리지 않고 바로 돌아옴)Futurefuture (미래에 채워질 결과)
wait_for_service를 빼먹으면서버가 아직 안 떠 있을 때 요청을 보내면 그 요청은 그냥 사라집니다. Topic과 달리 Service는 "보낼 상대가 있는지" 먼저 확인하는 습관을 들입니다.

실행기: spin 안에서 일어나는 일

rclpy.spin(node)은 내부적으로 실행기(executor)를 만들어 돌립니다. 기본 실행기는 스레드 하나로 동작하는 SingleThreadedExecutor입니다. 대기 중인 일(타이머, 도착한 메시지, 서비스 요청, 서비스 응답)을 하나 꺼내서 해당 콜백을 실행하고, 그 콜백이 끝나야 다음 일을 꺼냅니다.

교착 상태: 콜백 안에서 응답을 기다리면

이 구조 때문에 생기는 대표적인 문제가 있습니다. 타이머 콜백 안에서 서비스를 부르고 그 자리에서 응답을 기다리면, 프로그램이 영원히 멈춥니다.

def on_timer(self):
    result = self.cli.call(req)          # 동기 호출: 응답이 올 때까지 여기서 멈춤
    self.get_logger().info(f'{result.sum}')
  1. 실행기가 on_timer()를 실행합니다. 스레드 하나가 여기에 묶입니다.
  2. call()이 요청을 보내고 응답을 기다립니다.
  3. 응답이 도착합니다. 하지만 응답을 처리해 Future를 채우는 일도 같은 실행기의 몫이고, 실행기는 아직 on_timer()가 끝나기를 기다리는 중입니다.
  4. 콜백은 응답을, 실행기는 콜백을 서로 기다리며 둘 다 멈춥니다. 이것을 교착 상태(deadlock)라고 합니다.

해결 방법은 두 가지입니다. 첫째는 콜백 안에서 기다리지 않는 것입니다. call_async()로 보내고, 응답이 오면 불릴 함수를 Future에 등록해 둔 뒤 콜백을 바로 끝냅니다.

def on_timer(self):
    future = self.cli.call_async(req)
    future.add_done_callback(self.on_response)   # 응답이 오면 on_response 를 불러 달라
                                                 # on_timer 는 바로 끝남 → 실행기가 자유로워짐
def on_response(self, future):
    self.get_logger().info(f'sum = {future.result().sum}')

둘째는 실행기에 스레드를 여러 개 주는 것입니다. MultiThreadedExecutor를 쓰고, 동시에 실행되어도 되는 콜백들을 콜백 그룹으로 묶어 알려 줍니다.

확인 문제

서비스 서버의 콜백은 무엇을 받고 무엇을 반환하나?

요청 객체와 비어 있는 응답 객체를 받고, 응답 객체의 필드를 채워서 반환합니다. 반환한 응답이 클라이언트로 전달됩니다.

call_async()가 돌려주는 Future는 언제 채워지나?

응답이 도착하고, 실행기(spin)가 그 응답을 처리했을 때 채워집니다. spin하지 않으면 응답이 와도 Future는 비어 있습니다.

기본 실행기로 spin하는 노드의 타이머 콜백 안에서 self.cli.call(req)를 부르면 왜 멈추나?

기본 실행기는 스레드 하나라서 타이머 콜백이 끝나야 다음 일을 처리합니다. call()은 응답을 기다리는데, 응답을 처리할 실행기는 콜백이 끝나기를 기다리므로 서로를 기다리는 교착 상태가 됩니다.

위 문제를 해결하는 방법 두 가지는?

① call_async() 후 add_done_callback()으로 응답 처리 함수를 등록하고 콜백을 바로 끝낸다. ② MultiThreadedExecutor와 ReentrantCallbackGroup을 써서 다른 스레드가 응답을 처리할 수 있게 한다.

액션 서버

import time
import rclpy
from rclpy.node import Node
from rclpy.action import ActionServer
from action_tutorials_interfaces.action import Fibonacci


class FibonacciServer(Node):
    def __init__(self):
        super().__init__('fibonacci_action_server')
        self._server = ActionServer(self, Fibonacci, 'fibonacci', self.execute)

    def execute(self, goal_handle):                       # 수락된 목표마다 불림
        self.get_logger().info(f'목표 실행: order={goal_handle.request.order}')
        feedback = Fibonacci.Feedback()
        feedback.partial_sequence = [0, 1]

        for i in range(1, goal_handle.request.order):
            feedback.partial_sequence.append(
                feedback.partial_sequence[i] + feedback.partial_sequence[i - 1])
            goal_handle.publish_feedback(feedback)        # ② 피드백 발행
            time.sleep(1)

        goal_handle.succeed()                             # 상태를 SUCCEEDED 로
        result = Fibonacci.Result()
        result.sequence = feedback.partial_sequence
        return result                                     # ③ 결과

goal_handle은 목표 하나를 가리키는 손잡이입니다. 목표 내용(goal_handle.request)을 읽고, 피드백을 보내고, 최종 상태(succeed(), abort(), canceled())를 정하는 일을 모두 이것으로 합니다.

액션 클라이언트: 콜백의 연쇄

import rclpy
from rclpy.node import Node
from rclpy.action import ActionClient
from action_tutorials_interfaces.action import Fibonacci


class FibonacciClient(Node):
    def __init__(self):
        super().__init__('fibonacci_action_client')
        self._client = ActionClient(self, Fibonacci, 'fibonacci')

    def send_goal(self, order):
        goal = Fibonacci.Goal()
        goal.order = order
        self._client.wait_for_server()
        future = self._client.send_goal_async(goal, feedback_callback=self.on_feedback)
        future.add_done_callback(self.on_goal_response)       # ① 수락/거절 답이 오면

    def on_goal_response(self, future):
        goal_handle = future.result()
        if not goal_handle.accepted:
            self.get_logger().info('목표 거절됨')
            return
        self.get_logger().info('목표 수락됨')
        goal_handle.get_result_async().add_done_callback(self.on_result)   # ③ 결과가 오면

    def on_feedback(self, feedback_msg):                      # ② 피드백이 올 때마다
        self.get_logger().info(f'피드백: {list(feedback_msg.feedback.partial_sequence)}')

    def on_result(self, future):
        result = future.result().result
        self.get_logger().info(f'결과: {list(result.sequence)}')
        rclpy.shutdown()                                      # 결과를 받았으니 종료


def main():
    rclpy.init()
    node = FibonacciClient()
    node.send_goal(10)
    rclpy.spin(node)

목표 거절과 취소 받기

서버는 목표를 받을지 정하는 함수와, 취소 요청을 받을지 정하는 함수를 추가로 등록할 수 있습니다. 실행 중에 취소 요청이 들어왔는지는 goal_handle.is_cancel_requested로 확인합니다.

from rclpy.action import ActionServer, GoalResponse, CancelResponse
from rclpy.callback_groups import ReentrantCallbackGroup

self._server = ActionServer(
    self, Fibonacci, 'fibonacci', self.execute,
    goal_callback=self.on_goal,
    cancel_callback=self.on_cancel,
    callback_group=ReentrantCallbackGroup())

def on_goal(self, goal_request):
    if goal_request.order > 50:
        return GoalResponse.REJECT          # 너무 큰 목표는 거절
    return GoalResponse.ACCEPT

def on_cancel(self, goal_handle):
    return CancelResponse.ACCEPT

# execute 의 반복문 안에서
if goal_handle.is_cancel_requested:
    goal_handle.canceled()                  # 상태를 CANCELED 로
    return Fibonacci.Result(sequence=feedback.partial_sequence)
취소가 안 받아질 때위 서버의 execute는 time.sleep()으로 실행기를 붙잡고 있습니다. 기본 실행기(스레드 하나)라면 그동안 취소 요청을 처리할 스레드가 없어서, 취소가 일이 다 끝난 뒤에야 처리됩니다. 8장처럼 MultiThreadedExecutor로 spin하고 콜백 그룹을 ReentrantCallbackGroup으로 지정해야 실행 도중에 취소가 들어옵니다.

확인 문제

Action은 내부적으로 어떤 통신들로 이루어지나?

목표·결과·취소용 서비스 3개와, 피드백·상태용 토픽 2개로 이루어집니다.

목표 상태 ABORTED와 CANCELED의 차이는?

ABORTED는 서버가 스스로 목표 달성을 포기한 것(예: 경로를 찾을 수 없음)이고, CANCELED는 클라이언트의 취소 요청에 따라 멈춘 것입니다.

.action 파일의 세 부분은 위에서부터 무엇인가?

목표(goal), 결과(result), 피드백(feedback)입니다.

액션 클라이언트 코드에서 결과를 받을 때까지 기다리는 줄이 없는데 어떻게 결과를 받나?

add_done_callback()으로 "목표 응답이 오면", "결과가 오면" 부를 함수를 등록해 두고, spin()이 각 응답이 도착했을 때 그 함수들을 불러 줍니다.

"충전소로 이동"을 Service로 만들면 생기는 문제는?

이동하는 동안 클라이언트는 아무 정보도 받지 못하고, 중간에 다른 일이 생겨도 취소할 수 없습니다. 서버 콜백이 오래 붙잡혀 다른 요청도 처리하지 못합니다. 진행 보고와 취소가 되는 Action이 알맞습니다.

파라미터: 코드 밖으로 뺀 설정값

노드 안에서 바깥에서 받을 값을 파라미터로 선언합니다.

class Controller(Node):
    def __init__(self):
        super().__init__('controller')
        self.declare_parameter('max_speed', 0.5)          # 이름과 기본값 (기본값의 형식이 파라미터 형식)
        self.declare_parameter('robot_name', 'robot1')

        self.max_speed = self.get_parameter('max_speed').value
        name = self.get_parameter('robot_name').value
        self.get_logger().info(f'{name}: 최대 속도 {self.max_speed} m/s')
  • ROS 2에서는 파라미터를 먼저 선언(declare_parameter)해야 읽고 쓸 수 있습니다. 선언하지 않은 이름을 읽으면 오류가 납니다. 오타로 엉뚱한 이름을 쓰는 실수를 막기 위해서입니다.
  • 형식은 bool, int, float, string과 각각의 배열이 있습니다. 기본값이 0.5면 float 파라미터가 되어, 나중에 1(정수)을 넣으면 형식 오류가 납니다. 1.0으로 넣어야 합니다.
  • 위 코드는 값을 생성자에서 한 번만 읽습니다. 실행 중에 ros2 param set(4장)으로 바꾼 값을 반영하려면 쓸 때마다 다시 읽거나, add_on_set_parameters_callback()으로 바뀔 때 알림을 받아야 합니다.

리매핑: 코드를 고치지 않고 연결 바꾸기

리매핑(remapping)은 노드가 쓰는 토픽·서비스 이름을 실행할 때 바꾸는 기능입니다. 예를 들어 라이다 드라이버는 /scan으로 발행하는데, 가져다 쓰려는 장애물 인식 노드는 /lidar/scan을 구독하도록 작성되어 있다면, 둘 중 하나의 코드를 고치는 대신 실행할 때 이름을 이어 붙입니다.

$ ros2 run turtlesim turtle_teleop_key --ros-args -r /turtle1/cmd_vel:=/turtle2/cmd_vel   # 두 번째 거북이 조종

launch 인자로 설정 파일 고르기

launch 파일도 실행할 때 값을 받을 수 있습니다(launch 인자). 아래는 실행할 때 고른 설정 파일을 노드에 넣어 주는 launch 파일입니다.

import os
from ament_index_python.packages import get_package_share_directory
from launch import LaunchDescription
from launch.actions import DeclareLaunchArgument
from launch.substitutions import LaunchConfiguration, PathJoinSubstitution
from launch_ros.actions import Node


def generate_launch_description():
    config_dir = os.path.join(get_package_share_directory('my_robot_pkg'), 'config')
    params = PathJoinSubstitution([config_dir, LaunchConfiguration('params')])

    return LaunchDescription([
        DeclareLaunchArgument('params', default_value='params_real.yaml'),   # launch 인자 선언
        Node(package='my_robot_pkg', executable='driver', name='driver',
             parameters=[params]),
        Node(package='my_robot_pkg', executable='controller', name='controller',
             parameters=[params], output='screen'),
    ])

노드, 설정 파일, launch 파일은 각각 무엇을 담당하나?

시뮬레이션과 실제 로봇에서 최대 속도와 장치 경로가 다르다. 코드를 두 벌 만들지 않고 해결하는 방법은?

bringup 패키지에는 보통 무엇이 들어가나?

노드 코드 없이, 전체 시스템을 띄우는 launch 파일과 설정 파일만 들어갑니다.

기본값 0.5로 선언한 파라미터에 -p max_speed:=1을 주면 어떻게 되나?

float 파라미터에 정수를 넣는 것이므로 형식 오류가 납니다. 1.0으로 넣어야 합니다.

YAML 파일로 파라미터를 줬는데 기본값이 그대로 쓰인다. 무엇을 확인해야 하나?

YAML의 맨 위 이름이 실제 노드 이름(네임스페이스 포함)과 같은지, 그 아래에 ros__parameters:(밑줄 두 개)가 있는지 확인합니다. ros2 param get으로 실제 값을 볼 수 있습니다.

리매핑이란 무엇이고, 언제 쓰나?

노드가 쓰는 토픽·서비스 이름을 실행할 때 바꾸는 기능입니다. 서로 다른 이름을 쓰도록 작성된 두 노드를 코드 수정 없이 연결할 때 씁니다.

launch 파일을 만들었는데 ros2 launch가 "file not found"라고 한다. 원인은?

ros2 launch는 install/패키지/share/패키지/에서 찾습니다. setup.py의 data_files에 launch 디렉터리를 설치하도록 적고 다시 빌드해야 합니다.

트리 구조와 상대 위치

URDF의 링크와 조인트는 트리를 이룹니다. 맨 위에 루트 링크(보통 base_link)가 하나 있고, 모든 링크는 부모가 정확히 하나입니다. 고리(링크가 돌고 돌아 자기에게 돌아오는 연결)는 만들 수 없습니다.

각 조인트의 위치를 부모 기준의 상대 위치로 적는 덕분에, 아래 관절이 움직이면 그 위의 링크들이 자동으로 따라 움직입니다. 이 "부모 기준 상대 위치의 연쇄"가 12장 TF2의 핵심 개념이기도 합니다.

xacro: 반복을 줄이는 매크로

로봇팔처럼 비슷한 링크가 반복되면 URDF가 길고 고치기 어려워집니다. 링크 길이를 바꾸면 여러 곳의 숫자를 함께 고쳐야 하기 때문입니다. xacro는 URDF에 변수, 수식, 매크로(틀), 다른 파일 포함을 더한 형식입니다.

<robot name="arm" xmlns:xacro="http://www.ros.org/wiki/xacro">
  <xacro:property name="link_len" value="0.2"/>                 <!-- 변수 -->

  <xacro:macro name="arm_link" params="name">                   <!-- 틀 정의 -->
    <link name="${name}">
      <visual>
        <origin xyz="0 0 ${link_len/2 + 0.025}"/>              <!-- 수식 -->
        <geometry><box size="0.05 0.05 ${link_len}"/></geometry>
      </visual>
    </link>
  </xacro:macro>

  <xacro:arm_link name="Link1"/>                                <!-- 틀 사용 -->
  <xacro:arm_link name="Link2"/>
  <xacro:include filename="$(find my_robot)/urdf/gripper.xacro"/>  <!-- 다른 파일 포함 -->
</robot>
$ xacro arm.urdf.xacro > arm.urdf      # 매크로를 풀어서 보통 URDF로 변환

확인 문제

바퀴, 로봇팔의 관절, 몸체에 붙은 라이다는 각각 어떤 조인트 종류가 알맞나?

바퀴는 계속 도는 continuous, 로봇팔 관절은 범위가 있는 revolute, 라이다는 움직이지 않는 fixed입니다.

조인트의 <origin xyz="0 0 0.25"/>는 무엇을 기준으로 한 위치인가?

부모 링크의 좌표계 기준입니다. 바닥이나 로봇 전체 기준이 아닙니다.

<visual>과 <collision>의 모양을 다르게 두는 이유는?

visual은 보기 좋게 자세한 3D 모델을 쓰고, collision은 충돌 계산이 빠르도록 상자·원기둥 같은 단순한 모양을 쓰기 위해서입니다.

xacro를 쓰면 좋은 점은?

변수, 수식, 매크로, 파일 포함을 쓸 수 있어서 반복되는 링크를 한 번만 정의하고, 치수를 한 곳에서만 고치면 되므로 길고 실수하기 쉬운 URDF를 짧게 관리할 수 있습니다.

robot_state_publisher는 무엇을 입력받아 무엇을 내보내나?

URDF(robot_description 파라미터)와 관절 값(/joint_states)을 받아, 각 링크의 위치와 방향을 /tf(움직이는 관절)와 /tf_static(고정 관절)으로 발행합니다.

좌표계(frame)

좌표계는 원점 하나와 서로 수직인 x, y, z 세 축입니다. 로봇에는 좌표계가 여러 개 있습니다. 지도 전체의 좌표계, 로봇 몸체의 좌표계, 라이다의 좌표계, 카메라의 좌표계, 로봇팔 관절마다의 좌표계…. 센서 메시지의 header.frame_id(7장)가 바로 "이 값은 어느 좌표계 기준인가"를 나타냅니다.

ROS에서는 좌표축 방향을 통일해 두었습니다(REP 103). 로봇 몸체 기준으로 x는 앞, y는 왼쪽, z는 위이고, 오른손 좌표계입니다. 회전 방향은 축의 양의 방향에서 내려다볼 때 반시계 방향이 양수입니다. 길이는 미터, 각도는 라디안을 씁니다.

REPROS Enhancement Proposal (ROS 규약 문서)

좌표 변환: 이동 + 회전

좌표계 A에서 본 좌표계 B의 관계는 두 가지로 나타냅니다. B의 원점이 A에서 어디에 있는지(이동, translation)와, B의 축이 A의 축에 대해 얼마나 돌아가 있는지(회전, rotation)입니다. 이 둘을 4×4 행렬 하나로 묶은 것을 동차 변환 행렬이라고 합니다.

ᴬT_B = [ R   P ]      R: 3×3 회전 행렬 (B의 축이 A에서 어느 방향인가)
       [ 0   1 ]      P: 3×1 이동 벡터 (B의 원점이 A에서 어디인가)

이 행렬의 좋은 점은 곱하면 이어진다는 것입니다. A→B, B→C를 알면 곱해서 A→C를 얻습니다.

ᴬT_C = ᴬT_B · ᴮT_C

예를 들어 계산해 봅니다. 문제를 단순하게 하려고 바닥 평면(x, y)과 z축 회전만 봅니다.

회전을 나타내는 두 가지 방법

오일러 각 (Roll, Pitch, Yaw)

x축 회전(roll, 옆으로 기울기), y축 회전(pitch, 앞뒤로 숙이기), z축 회전(yaw, 고개 돌리기) 세 각도입니다. 사람이 이해하기 쉬워서 URDF의 rpy나 설정 파일에 씁니다. 하지만 특정 자세(pitch가 ±90°)에서 두 축이 겹쳐 한 방향의 회전을 표현할 수 없게 되는 짐벌 락 문제가 있고, 회전을 이어 붙이는 계산이 번거롭습니다.

쿼터니언 (x, y, z, w)

숫자 네 개로 회전을 나타냅니다. 짐벌 락이 없고, 회전을 이어 붙이는 계산(곱셈)이 빠르고 안정적이어서 ROS 메시지의 회전은 모두 쿼터니언입니다(geometry_msgs/Quaternion). 대신 숫자만 보고 어떤 회전인지 알기 어렵습니다.

바닥 위 로봇처럼 z축 회전(yaw = θ)만 있을 때는 쿼터니언이 간단합니다: (x, y, z, w) = (0, 0, sin(θ/2), cos(θ/2)). 회전이 없으면 (0, 0, 0, 1)입니다. (0, 0, 0, 0)은 올바른 쿼터니언이 아니므로, 메시지를 직접 만들 때 w를 빠뜨리면 안 됩니다.

from tf_transformations import quaternion_from_euler, euler_from_quaternion
# 설치: sudo apt install ros-humble-tf-transformations && pip3 install transforms3d

q = quaternion_from_euler(0.0, 0.0, 1.5708)      # roll, pitch, yaw → (x, y, z, w)
# q ≈ (0.0, 0.0, 0.7071, 0.7071)
roll, pitch, yaw = euler_from_quaternion(q)

TF 트리

TF2는 좌표계들의 관계를 URDF처럼 트리로 관리합니다. 각 좌표계는 부모가 하나이고, 부모에 대한 변환 하나만 누군가가 알려 주면 됩니다. 그러면 TF2가 트리를 따라 경로를 찾아 변환을 곱해서, 트리 안의 어떤 두 좌표계 사이의 변환이든 계산해 줍니다.

좌표계뜻성질
map지도에 고정된 좌표계오래 지나도 정확함. 대신 위치 추정이 오차를 바로잡을 때 로봇 위치가 갑자기 뛸 수 있음
odom로봇이 출발한 곳에 고정된 좌표계. 바퀴 회전 수 등으로 움직인 양을 누적값이 끊김 없이 부드럽게 변해 짧은 시간의 제어에 좋음. 하지만 바퀴 미끄러짐 등으로 오차가 계속 쌓임

map과 base_link 사이에 odom을 두는 이유는, 둘의 장점을 함께 쓰기 위해서입니다. 위치 추정 노드는 "map에서 본 로봇 위치"를 계산하지만, map→base_link를 직접 발행하지 않고 오도메트리의 누적 오차만큼을 map→odom으로 발행합니다. 그래서 odom→base_link는 부드럽게 유지되면서도, 둘을 곱한 map→base_link는 정확해집니다.

broadcaster: 변환 알려 주기

turtlesim의 거북이 위치(/turtle1/pose)를 받아서 world → turtle1 변환으로 발행하는 노드입니다. 거북이를 움직이면 turtle1 좌표계가 따라 움직입니다.

from geometry_msgs.msg import TransformStamped
from tf2_ros import TransformBroadcaster
from tf_transformations import quaternion_from_euler
from turtlesim.msg import Pose

class TurtleBroadcaster(Node):
    def __init__(self):
        super().__init__('turtle_tf_broadcaster')
        self.br = TransformBroadcaster(self)
        self.create_subscription(Pose, '/turtle1/pose', self.on_pose, 10)

    def on_pose(self, msg):
        t = TransformStamped()
        t.header.stamp = self.get_clock().now().to_msg()   # 언제의 변환인가
        t.header.frame_id = 'world'                        # 부모
        t.child_frame_id = 'turtle1'                       # 자식
        t.transform.translation.x = msg.x
        t.transform.translation.y = msg.y
        q = quaternion_from_euler(0, 0, msg.theta)         # 평면 위 회전 → 쿼터니언
        t.transform.rotation.x, t.transform.rotation.y = q[0], q[1]
        t.transform.rotation.z, t.transform.rotation.w = q[2], q[3]
        self.br.sendTransform(t)

움직이지 않는 변환은 코드를 쓸 필요 없이 명령 한 줄로 발행할 수 있습니다. 센서를 로봇에 새로 달았는데 URDF에 아직 넣지 않았을 때 자주 씁니다.

listener: 변환 물어보기

from tf2_ros import TransformException
from tf2_ros.buffer import Buffer
from tf2_ros.transform_listener import TransformListener

# 생성자에서
self.buffer = Buffer()                                 # 받은 변환을 시간과 함께 보관 (기본 10초)
self.listener = TransformListener(self.buffer, self)   # /tf, /tf_static 을 구독해 buffer 에 채움

# 타이머 콜백 등에서
try:
    t = self.buffer.lookup_transform('turtle2', 'turtle1', rclpy.time.Time())
except TransformException as ex:
    self.get_logger().info(f'변환을 찾을 수 없음: {ex}')
    return
# t.transform.translation = turtle2 좌표계에서 본 turtle1 의 위치

lookup_transform(target, source, time)은 "source 좌표계의 값을 target 좌표계로 바꾸는 변환"을 돌려줍니다. 결과의 이동 값은 곧 "target에서 본 source 원점의 위치"입니다. 위 예에서는 turtle2의 눈으로 본 turtle1의 위치이므로, x가 양수면 turtle1이 앞에 있고, atan2(y, x)가 turtle1 쪽 방향입니다. 이 값으로 turtle2에게 속도 명령을 보내면 turtle2가 turtle1을 따라가게 만들 수 있습니다.

시간이 중요한 이유Buffer는 변환을 시간별로 보관합니다. 0.1초 전에 찍은 라이다 데이터는 0.1초 전의 로봇 위치로 바꿔야 정확하기 때문입니다. 세 번째 인자 rclpy.time.Time()(값이 0인 시간)은 "가지고 있는 가장 최근 것"이라는 뜻이고, 메시지의 header.stamp를 넣으면 그 시각의 변환을 계산합니다. 아직 받지 못한 미래 시각을 물으면 "extrapolation into the future" 오류가 납니다.

TF 문제의 흔한 원인
  • 트리가 끊김: 어떤 연결을 아무도 발행하지 않으면 그 아래 좌표계는 위쪽과 변환할 수 없습니다. view_frames로 트리가 하나로 이어져 있는지 봅니다.
  • 부모가 둘: 두 노드가 같은 자식 좌표계를 서로 다른 부모로 발행하면 트리가 깨집니다. 예: 위치 추정 노드와 다른 노드가 모두 odom→base_link를 발행.
  • 시간이 안 맞음: 시뮬레이션이나 bag 재생 중에 일부 노드만 use_sim_time을 켜면, 변환의 시각이 서로 맞지 않아 lookup이 실패합니다.

확인 문제

ROS에서 로봇 몸체 기준 x, y, z축은 각각 어느 방향인가?

x는 앞, y는 왼쪽, z는 위입니다(REP 103).

A→B 변환과 B→C 변환을 알 때 A→C 변환은 어떻게 구하나?

두 동차 변환 행렬을 곱합니다: ᴬT_C = ᴬT_B · ᴮT_C.

ROS 메시지가 회전을 오일러 각이 아닌 쿼터니언으로 나타내는 이유는?

쿼터니언은 짐벌 락이 없고, 회전을 이어 붙이는 계산이 빠르고 안정적이기 때문입니다.

yaw가 0인(회전 없는) 쿼터니언은? 실수로 (0, 0, 0, 0)을 넣으면?

(x, y, z, w) = (0, 0, 0, 1)입니다. (0, 0, 0, 0)은 올바른 회전이 아니라서 변환 계산이 실패하거나 RViz2에서 표시되지 않습니다.

odom→base_link와 map→odom은 각각 누가 발행하나? map과 odom의 차이는?

odom→base_link는 오도메트리(바퀴 엔코더, IMU) 노드가, map→odom은 위치 추정 노드(AMCL, SLAM)가 발행합니다. odom은 부드럽게 변하지만 오차가 쌓이고, map은 오래 지나도 정확하지만 보정할 때 값이 뛸 수 있습니다.

라이다와 몸체 사이의 변환은 /tf와 /tf_static 중 어디로 발행하나? 이유는?

/tf_static입니다. 라이다는 몸체에 고정되어 변환이 변하지 않으므로 한 번만 발행하면 되고, TRANSIENT_LOCAL QoS 덕분에 나중에 켜진 노드도 받을 수 있습니다.

buffer.lookup_transform('base_link', 'laser', Time())의 결과는 무엇을 뜻하나?

laser 좌표계의 값을 base_link 좌표계로 바꾸는 가장 최근의 변환입니다. 그 이동 값은 base_link에서 본 라이다의 위치입니다.
